4. Risk Notes

  • The three operations are independent (predecessor 0x0, same ETA 2026-11-17 18:29:47 UTC); any executor may run them in any order. The new BTC.b implementation reads AssetRouter.depositFee() on every proof mint, and the current AssetRouter implementation has no such function (the call reverts at the pinned block): if the BTC.b upgrade executes before the AssetRouter upgrade, BTC.b proof mints revert until the router is upgraded.
  • No initializer runs (upgradeAndCall with empty data). Every per-token deposit fee starts at 0, so nothing is charged on execution. The minimum stays 2,000 sats (0.00002 BTC): the storage field is renamed minRequestAmount (oz-renamed-from), and non-BTC redeems are now held to it too.
  • After the upgrade a non-zero fee is split off every proof mint and minted to the token treasury. OPERATOR_ROLE can set it to 100-1,000 sats per mint without the timelock. Any other value needs DEFAULT_ADMIN_ROLE (the timelock), and the fee is capped at half the minimum.
  • BaseLBTC.unpauseTransfers moves from DEFAULT_ADMIN_ROLE (the 1-day timelock) to MANAGER_ROLE, the role that already clears the mint/burn pause: resuming paused transfers no longer waits for the timelock.
  • All three were scheduled in one Safe transaction (0xf18a01875814c62d83b089f6565c9e02a80c296fdb81306d04d44f11e795ae05) sent to 0x251a604e8e8f6906d60f8dedc5aaeb8cd38f4892, the same Safe that BTC.b and LBTC name as treasury: the deposit-fee recipient after the upgrade.
  • AssetRouter.changeNativeToken no longer deletes the previous native token's route. Storage stays append-only: TokenConfig gains depositFee at the end of a mapped struct, and AssetRouterStorage appends maxDepositFee + feeTokens in its ERC-7201 namespace. OpenZeppelin libraries are bumped in all three implementations.
